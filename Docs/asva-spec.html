Executive Summary

The Autonomous Stardew Valley Agent (ASVA) is a local-first, open-source AI system that autonomously plays Stardew Valley from game start through late-game milestones. The agent integrates with the game via SMAPI, extracts real-time game state, reasons about long-horizon goals using a local Ollama LLM, and dispatches deterministic, tick-accurate in-game actions.

ASVA is not a scripted bot. It is a goal-directed, memory-equipped, multi-layer reasoning agent that adapts its behavior based on season, resource availability, community center bundle progress, and economic state. Every decision traces back to a strategic plan formed by the LLM and decomposed into executable micro-tasks by deterministic planners.

Design Philosophy: The LLM is used exclusively for high-latency strategic and tactical decisions. Execution — action sequencing, pathfinding, tick-level game interaction — is always deterministic code. This separation guarantees reproducibility, fault isolation, and acceptable latency.

Primary Goals

  • Complete the Community Center (all bundles) as efficiently as possible across in-game seasons
  • Maximize per-season gold through optimal crop selection, foraging, fishing, and mining strategies
  • Reach late-game milestones: all tools upgraded, all skills at level 10, Skull Cavern depth 100+
  • Maintain zero human intervention after session initialization
  • Provide full observability: every decision is logged with its LLM rationale and execution trace

Non-Goals (v1.0)

  • Multiplayer support (co-op farm)
  • Cloud inference — all LLM calls remain local via Ollama
  • Real-time streaming play for human entertainment (no performance loop constraints)
  • Support for mods that alter base game mechanics

System Architecture

ASVA is structured as a four-layer agent architecture separated by planning horizon. Each layer communicates exclusively downward through typed interfaces. No layer calls upward, and no layer skips a layer below it. This strict dependency direction (matching GEMINI Rule 02) ensures testability and allows individual layers to be replaced independently.

L4 Strategic
StrategicPlanner GoalManager SeasonalAdvisor BundleTracker
L3 Tactical
DayPlanner TaskScheduler ResourceOptimizer ReplanEngine
L2 Execution
ActionDispatcher Pathfinder InventoryManager DialogHandler CombatController
L1 Infrastructure
SMAPIBridge OllamaClient StateRepository MemoryStore Logger ConfigLoader

Cross-Cutting Components

Three components sit outside the layer stack and are accessible by all layers. They are injected via dependency injection, never imported directly.

cross-cuttingEventBus
Typed pub/sub for inter-layer events. Layers subscribe to events (e.g., day.ended, task.failed) rather than calling upward. Prevents coupling.
cross-cuttingObservabilityService
Structured JSON logging, metrics emission, and decision trace recording. Every layer emits structured log entries via this service — never raw console.log.
cross-cuttingErrorBoundary
Catches unhandled errors at layer boundaries. Triggers recovery procedures: task retry → replan → safe state → agent pause. Never swallows errors silently.

Process Topology

ASVA runs as two processes that communicate over a local Unix socket:

ProcessRuntimeRoleRestartable?
asva-agentNode.js 20+All four layers, state management, LLM orchestration, REST API serverYes — state persisted to disk

SMAPI Bridge Constraint: The bridge runs inside the game process as a SMAPI mod. It communicates exclusively via WebSocket (port 7890 by default). The agent process never accesses game memory directly — all game interaction routes through the bridge. This is the only supported integration boundary.

Decision Loop — Main Cycle

The agent runs one continuous decision loop. The loop is intentionally separated into slow (LLM) and fast (deterministic) phases:

while (agentRunning) {
  const state = await smapiBridge.getGameState();       // pull current tick state

  if (state.event === 'DAY_START') {
    const plan = await tacticalLayer.planDay(state);     // LLM-assisted, ~1–5s
    executionLayer.loadDayPlan(plan);
  }

  const nextAction = executionLayer.getNextAction(state); // deterministic, <1ms
  if (nextAction) {
    await smapiBridge.dispatch(nextAction);
  }

  if (executionLayer.isBlocked()) {
    await replanEngine.replan(state, executionLayer.getBlockedTask()); // LLM if needed
  }

  await sleep(TICK_INTERVAL_MS);                         // default: 50ms
}

Module Responsibilities

L4 — Strategic Layer

strategicStrategicPlanner
Invoked at season start and after major goal completion. Produces a multi-week goal tree using LLM reasoning over full game state context. Outputs StrategicPlan with prioritized objectives and estimated timelines.
strategicGoalManager
Maintains the active goal stack. Supports goal preemption (higher priority goal interrupts current), deferral, and completion detection. All goal state is persisted — survives agent restart.
strategicSeasonalAdvisor
Provides season-aware crop calendars, foraging schedules, and fishing spot recommendations. Data-driven from static game data tables. No LLM needed — pure computation over known game mechanics.
strategicBundleTracker
Syncs Community Center bundle state from game. Tracks needed items, seasonal availability windows, and minimum item quantities. Emits bundle.item.available events to trigger acquisition tasks.

L3 — Tactical Layer

tacticalDayPlanner
Core of day-to-day operation. Takes strategic goals + current game state, calls LLM to produce an ordered DayPlan (list of TaskBlocks). Respects stamina budget, time constraints, weather, and shop hours.
tacticalTaskScheduler
Converts DayPlan into a time-ordered queue of Task objects with dependencies. Handles task prioritization, prerequisite chaining, and estimated duration tracking.
tacticalResourceOptimizer
Evaluates crop selection, tool usage, energy allocation, and time budget. Provides LP-style (linear programming analogy) scoring for competing task sets. Outputs optimization report attached to each plan.
tacticalReplanEngine
Activated on task failure. Classifies failure type (blocked path, missing item, insufficient energy, NPC unavailable). Attempts deterministic fix first; escalates to LLM replan if fix fails. Implements back-off to prevent replan loops.

L2 — Execution Layer

executionActionDispatcher
Translates abstract Task objects into concrete SMAPI GameAction sequences. Manages action retry logic, timeout detection, and success validation. Single responsibility: bridge tasks to bridge actions.
executionPathfinder
A* pathfinding over the game map tile graph. Supports multi-map routing (farm → town → mine). Tile graph is cached and rebuilt on map load. Pathfinding runs synchronously — must complete in <5ms for any route.
executionInventoryManager
Tracks player inventory state. Handles item sorting, tool equipping, chest storage/retrieval, and sell decisions. Provides hasItem(id, qty), equipTool(type), and optimizeLoadout(activity) APIs.
executionDialogHandler
Detects and manages all in-game dialog, menu, and UI states. Dismisses non-essential dialogs. Routes shop interactions to transactional buy/sell logic. Handles quest acceptance/completion.
executionCombatController
Manages mine/Skull Cavern combat. Implements dodge timing, weapon selection, bomb usage, and retreat triggers. Pure reactive — no LLM involved. Falls back to safe retreat if health drops below threshold.

L1 — Infrastructure Layer

infrastructureSMAPIBridge
WebSocket client to the SMAPI mod. Handles connection, reconnection, message framing, and event deserialization. Provides typed GameStateSnapshot and dispatch(GameAction) interface. All game I/O routes here.
llmOllamaClient
HTTP client for Ollama REST API. Implements prompt construction, response parsing, retry-on-timeout, model health checks, and response caching for identical prompts. Tracks token usage and latency per call.
infrastructureStateRepository
SQLite-backed persistence layer. Stores game snapshots, strategic plans, task history, and bundle state. All writes are transactional. Exposes typed repository interfaces — no SQL in upper layers.
infrastructureMemoryStore
Episodic and semantic memory for the agent. Stores experience records (e.g., "fishing at forest pond in summer gives 40% catfish rate"), used as context in planning prompts. Vector-free — simple relevance retrieval by tag and season.

State Snapshot — Recovery Protocol

On crash or unexpected shutdown, the agent recovers via a deterministic snapshot protocol:

  1. Agent starts, reads latest AgentState snapshot from SQLite
  2. Reconnects to SMAPI Bridge — requests current GameStateSnapshot
  3. Compares game day in snapshot vs. live state — detects any days elapsed while agent was down
  4. If same day: resumes task queue at last completed task
  5. If day advanced: triggers tactical replan for current day before resuming
  6. If season changed: triggers full strategic replan before tactical

LLM Integration Strategy

The LLM is a slow, high-quality advisor — not an action controller. All calls to Ollama are asynchronous, bounded by timeouts, retried on failure, and their results are validated before use. The execution layer never waits for an LLM call; LLM calls happen between action cycles.

When the LLM is Called

TriggerCallerFrequencyExpected LatencyFallback
Season startStrategicPlanner4× per year3–8sPrevious season plan template
Day startDayPlannerDaily1–4sDefault activity priority list
Task blocked 3× in successionReplanEngineOn demand1–3sSkip task, advance queue
Unexpected game eventEventBus handlerRare1–3sPause and log for human review

Prompt Architecture

Each LLM call uses a structured prompt with four sections. This structure is enforced by the prompt template system — free-form prompts are not allowed.

# CONTEXT
You are the strategic planner for an autonomous Stardew Valley agent.
Today is Day {{gameDay}}, {{season}} Year {{year}}.
Current gold: {{gold}}g. Stamina: {{stamina}}/{{maxStamina}}.

# GAME STATE
{{compressedGameState}}  <-- JSON, max 2000 tokens

# MEMORY
{{relevantMemories}}     <-- top-5 relevant experience records

# TASK
Generate a day plan as a JSON array of TaskBlock objects.
Each TaskBlock must include: activity, location, estimatedDuration, energyCost, priority.
Respond ONLY with a JSON array. No explanation, no markdown, no preamble.
P0 — Response Validation: Every LLM response is parsed through a Zod schema before use. Invalid responses trigger a structured retry (max 3 attempts with corrective prompt). If all retries fail, the system falls back to the deterministic fallback plan. The agent never executes an action derived from an unvalidated LLM response.

Ollama Client Design

// infrastructure/ollama-client.ts

interface OllamaCallOptions {
  promptTemplate: string;
  variables: Record<string, unknown>;
  responseSchema: ZodSchema;
  timeout?: number;          // default: 15000ms
  maxRetries?: number;       // default: 3
  cacheable?: boolean;       // default: false
}

class OllamaClient {
  async call<T>(options: OllamaCallOptions): Promise<OllamaResult<T>> {
    const prompt = this.renderTemplate(options.promptTemplate, options.variables);
    const cacheKey = this.hashPrompt(prompt);

    if (options.cacheable) {
      const cached = await this.cache.get(cacheKey);
      if (cached) return cached;
    }

    const startMs = Date.now();
    let lastError: Error | null = null;

    for (let attempt = 0; attempt < (options.maxRetries ?? 3); attempt++) {
      try {
        const raw = await this.httpPost('/api/generate', { prompt, model: this.model });
        const parsed = options.responseSchema.parse(JSON.parse(raw.response));
        const result = { data: parsed, latencyMs: Date.now() - startMs, attempt };
        this.observability.logDecision({ prompt, raw: raw.response, parsed, ...result });
        return result;
      } catch (error) {
        lastError = error as Error;
        this.logger.warn('OllamaClient: attempt failed', { attempt, error });
      }
    }

    throw new AppError('OLLAMA_CALL_FAILED', 'All retry attempts exhausted', 500, { cause: lastError });
  }
}

Agent Control

POST /api/v1/control/pause Pause agent execution ▶

Pauses the agent decision loop after completing the current action. Game is not paused — only agent action dispatch is suspended. Safe to call at any time.

// 200 OK
{ "success": true, "data": { "status": "paused", "pausedAt": "2024-03-15T09:15:00Z" } }
POST /api/v1/control/resume Resume agent execution ▶

Resumes the paused agent. If a day plan was active, execution continues from the last incomplete task.

POST /api/v1/control/replan Force a replanning cycle ▶

Discards the current day plan and triggers an immediate LLM replanning call. Useful for testing or when the user wants to inject a goal override. Requires the agent to be paused.

Request Body

Error Handling & Recovery

Error handling follows GEMINI Rule 02 strictly: typed AppError class, no silent failures, unhandled rejections caught at process level, no stack traces exposed in API responses. The agent has four recovery escalation levels before entering a safe pause state.

Escalation Hierarchy

LevelTriggerRecovery ActionLatency Budget
L1 — RetrySingle action failsRetry same action up to 3 times with 100ms backoff<500ms
L2 — SkipAction fails 3× in sequenceMark task failed, skip to next task in queueImmediate
L3 — Deterministic ReplanCore task cannot be completed (missing item, wrong location)ReplanEngine attempts rule-based fix without LLM<100ms
L4 — LLM ReplanDeterministic fix fails or task is critical pathLLM generates new partial day plan<10s
L5 — Safe PauseLLM replan fails or bridge disconnectedAgent pauses, logs full state, waits for human intervention signalImmediate

Error Code Taxonomy

CodeCategoryDescriptionRecovery
BRIDGE_DISCONNECTEDInfrastructureWebSocket to SMAPI bridge closed unexpectedlyReconnect with exponential backoff (max 60s)
BRIDGE_TIMEOUTInfrastructureBridge did not respond to action within 2sRetry action × 3, then skip
OLLAMA_UNAVAILABLELLMOllama HTTP endpoint unreachableUse cached fallback plan; alert via observability
OLLAMA_TIMEOUTLLMLLM response exceeded 15s timeoutRetry × 3 with same prompt
LLM_INVALID_RESPONSELLMLLM response fails Zod schema validationRetry with corrective prompt × 3, then fallback
PATH_NOT_FOUNDExecutionA* finds no valid path between two pointsAttempt alternate route via waypoints
STAMINA_EXHAUSTEDExecutionPlayer stamina at zero before tasks completeSkip remaining tasks, go to sleep immediately

SMAPI Bridge Reconnection

class SMAPIBridge {
  private async reconnect(): Promise<void> {
    const delays = [1000, 2000, 5000, 10000, 30000, 60000]; // ms backoff steps
    for (const delay of delays) {
      await sleep(delay);
      try {
        await this.connect();
        this.logger.info('SMAPIBridge: reconnected successfully');
        this.eventBus.emit('bridge.reconnected');
        return;
      } catch {
        this.logger.warn('SMAPIBridge: reconnect attempt failed', { delay });
      }
    }
    // All attempts exhausted — enter safe pause
    this.eventBus.emit('agent.safe-pause', { reason: 'BRIDGE_DISCONNECTED' });
  }
}

Scalability Considerations

ASVA v1.0 is designed for single-machine, single-game-instance operation. However, the architecture supports two natural scaling dimensions: running multiple parallel agent sessions and replacing the LLM backend with a more powerful model or remote inference server.

Horizontal Scaling — Multi-Session

To run N parallel game sessions (for research or speedrun comparison):

  • Each agent instance gets its own SQLite database and port assignment (config.yaml per instance)
  • The SMAPI bridge port (7890) must be unique per instance — configurable via ASVA_BRIDGE_PORT
  • Ollama handles concurrent requests natively — no agent-side changes needed for up to ~4 concurrent sessions on adequate hardware
  • For >4 sessions, introduce an OllamaRequestQueue to serialize calls and prevent GPU memory overflow

LLM Backend Upgrade Path

The OllamaClient is the only LLM integration point. Replacing it requires only implementing the same interface:

interface LLMClient {
  call<T>(options: OllamaCallOptions): Promise<OllamaResult<T>>;
  healthCheck(): Promise<boolean>;
}
// Swap Ollama for Claude API, vLLM, or LM Studio by implementing this interface

Trade-offs & Design Decisions

Decision

Deterministic execution layer vs. LLM-driven execution

Choice Made

Deterministic execution, LLM only for planning

Rationale

LLM latency (1–8s) makes per-action calls impossible at 50ms tick rate. Determinism enables reliable testing and replay. See ADR-003.

Decision

WebSocket vs. shared memory for SMAPI bridge

Choice Made

Local WebSocket (port 7890)

Rationale

SMAPI runs in a .NET process; Node.js agent cannot access its memory directly. WebSocket provides clean process boundary, is debuggable, and supports reconnection. See ADR-001.

Decision

SQLite vs. PostgreSQL for state persistence

Choice Made

SQLite with WAL mode

Rationale

Single-machine deployment, low concurrency, zero infrastructure. SQLite in WAL mode handles the agent's write patterns without contention. Easy backup (file copy). See ADR-002.

Decision

Tag-based memory retrieval vs. vector embeddings

Choice Made

Tag-based retrieval (season, activity, location)

Rationale

Game domain is small and structured. Tag-based retrieval is fully deterministic, zero external dependencies, and faster than embedding lookup. Can upgrade to vector retrieval in v2 if memory corpus grows beyond ~10K records.

Decision

Monorepo vs. separate repositories for agent and bridge

Choice Made

Monorepo with pnpm workspaces

Rationale

Shared types package requires atomic versioning across both apps. Monorepo allows a single PR to update the protocol on both sides simultaneously, preventing contract drift.

Decision

Prompt stored in files vs. embedded in code

Choice Made

Versioned Markdown files in /prompts/

Rationale

Prompts need independent versioning, diff visibility in PRs, and searchability. File-based prompts enable prompt engineers to iterate without touching TypeScript. Version suffix enables reproducibility of past decisions. See ADR-004.

Known Risk Register

RiskSeverityProbabilityMitigation
LLM produces plans that are semantically valid JSON but logically incoherent (hallucinated crops, impossible schedules)HighMediumZod validates structure; ResourceOptimizer validates feasibility; implausible plans trigger replan

Future Enhancements

v1.1 — Observability Dashboard

A local web UI (React + Vite, served by the agent API server) that visualizes: the agent's current location on the farm map, today's task queue and completion status, real-time gold/stamina metrics, and a decision trace explorer showing each LLM planning call. All data consumed from the existing REST API — no new backend work required.

v1.2 — Vector Memory

Replace the tag-based MemoryStore with a local vector store (e.g., vectra or chroma via Docker) for semantic memory retrieval. Enable the agent to surface relevant past experiences with greater precision — for example, "which fishing spots were most profitable during rainy summer days" without requiring an exact tag match.

v1.3 — Multi-Goal Parallelism

Extend the TaskScheduler to support interleaved task execution — for example, watering crops while waiting for NPCs to become available, or mining in the morning and then switching to social objectives in the evening. The current scheduler is strictly sequential per task block.

v2.0 — Multi-Agent Research Mode

Run 8–16 parallel agent instances with different Ollama models, prompt versions, or strategic configurations. Compare outcomes across runs: Community Center completion date, total gold earned, agent passout rate. Enables systematic evaluation of LLM planning quality across models and prompt iterations. Requires the OllamaRequestQueue and a central results aggregation database.

v2.1 — Reinforcement Fine-Tuning Data Collection

Emit structured (state, decision, outcome) tuples from each game session in a format suitable for supervised fine-tuning or RLHF. The goal: train a purpose-built Stardew Valley planning model that outperforms general-purpose LLMs on this specific domain, with dramatically lower inference latency.

Open Source Roadmap: All v1.x features will be released under MIT license with full documentation. The repository will include a CONTRIBUTING.md, architecture decision records for all major decisions, and a reproducible dev environment via Docker Compose (for Ollama) and a seed-data script that starts a fresh Spring Year 1 game state without requiring an actual game copy.
